1. Le projet : TaskFlow

Un outil de gestion de projets multi-équipes, dans l'esprit de Jira ou Trello. Le domaine est assez riche pour pratiquer le DDD, le temps réel, les événements et la sécurité fine.

  • Workspaces (tenant) → Projets → Tâches sur un board Kanban (glisser-déposer)
  • Membres et rôles par workspace : Owner, Admin, Member, Viewer (autorisation par ressource)
  • Commentaires, mentions @, pièces jointes, historique d'audit
  • Mises à jour temps réel du board avec SignalR
  • Notifications asynchrones (e-mail simulé) via une file de messages
  • Tableau de bord : statistiques par projet, tâches en retard

4. Architecture

Clean Architecture + Vertical Slices (modular monolith)

On combine deux idées. La Clean Architecture impose que les dépendances pointent vers le domaine. Les Vertical Slices rangent le code par fonctionnalité plutôt que par couche technique. Chaque module (Projects, Tasks, Identity, Notifications) est autonome et pourra devenir un microservice plus tard.

TaskFlow/
├─ src/
│  ├─ TaskFlow.AppHost/            # Aspire : orchestration locale
│  ├─ TaskFlow.ServiceDefaults/    # OpenTelemetry, health checks, résilience
│  ├─ TaskFlow.Api/                # Hôte : Program.cs, middlewares, endpoints
│  ├─ Modules/
│  │  ├─ Tasks/
│  │  │  ├─ TaskFlow.Tasks.Domain/          # Entités, Value Objects, événements, règles
│  │  │  ├─ TaskFlow.Tasks.Application/     # Features/CreateTask/{Command, Handler, Validator, Endpoint}
│  │  │  ├─ TaskFlow.Tasks.Infrastructure/  # DbContext, repositories, outbox
│  │  │  └─ TaskFlow.Tasks.Contracts/       # Événements publics (communication entre modules)
│  │  ├─ Projects/ …
│  │  └─ Notifications/ …
│  └─ TaskFlow.SharedKernel/       # Result, Entity, AggregateRoot, DomainEvent
├─ web/taskflow-ui/                # Angular 21
├─ tests/ (Unit, Integration, Architecture, E2E)
├─ .github/workflows/
├─ Directory.Build.props           # Options communes : Nullable, TreatWarningsAsErrors, analyseurs
└─ Directory.Packages.props        # Versions des paquets NuGet centralisées
Règles d'or
  • Le Domain ne référence rien, ni EF Core ni ASP.NET.
  • Un module ne lit jamais directement la base d'un autre module. Il passe par ses Contracts ou par des événements.
  • Chaque module a son propre schéma Postgres et son propre DbContext.
  • Ces règles sont vérifiées automatiquement par des tests d'architecture.

5. Backend : les notions à retenir

DDD tactique

  • Aggregate Root : seul point d'entrée pour modifier un ensemble cohérent (ex. Project contient ses Columns). On ne modifie qu'un agrégat par transaction.
  • Value Object : immuable, comparé par sa valeur (TaskTitle, Email, DueDate). On l'implémente avec un record et une factory qui valide.
  • Invariants : les règles métier vivent dans l'entité (setters privés, méthodes comme task.MoveTo(column)).
  • Domain Events : TaskAssignedEvent est levé par l'entité puis dispatché au SaveChanges.
  • Identifiants fortement typés : readonly record struct TaskId(Guid Value). On utilise Guid.CreateVersion7(), qui donne des identifiants triables et plus efficaces en index.

CQRS et pipeline

  • Les Commands modifient l'état et retournent un Result. Les Queries lisent (AsNoTracking, projection directe en DTO, voire Dapper).
  • Des behaviors (middlewares de pipeline) gèrent les aspects transverses : validation, logging, transaction, cache.
  • Result pattern : une erreur métier attendue renvoie un Result.Failure(Error) et ne lève pas d'exception. Les exceptions restent réservées aux cas vraiment exceptionnels.

API (Minimal APIs)

  • Utilise MapGroup(), TypedResults, et un fichier d'endpoint par feature (interface IEndpoint scannée au démarrage).
  • Les erreurs sortent au format ProblemDetails (RFC 9457) via AddProblemDetails() et IExceptionHandler.
  • Versionne l'API avec Asp.Versioning et génère le document OpenAPI nativement.
  • Ajoute le rate limiting intégré, l'output caching, et un ETag / If-Match pour la concurrence optimiste.
  • Les requêtes de modification portent une clé d'idempotence (en-tête Idempotency-Key).

EF Core 10

  • Configure les entités avec IEntityTypeConfiguration<T> et des value converters pour les identifiants typés. Mappe les Value Objects en complex types ou owned types.
  • Gère la concurrence avec la colonne xmin de Postgres comme jeton de concurrence.
  • Utilise des interceptors pour l'audit (CreatedAt/By) et le soft delete (filtre global).
  • Applique les migrations en CI/CD via un bundle (dotnet ef migrations bundle), jamais au démarrage en production.
  • Anticipe les problèmes de performance : requêtes N+1, AsSplitQuery, pagination par curseur (keyset) plutôt que Skip/Take sur les grosses tables.

Messagerie fiable

  • Outbox pattern : l'événement est écrit dans la même transaction que les données, puis publié par un processus en arrière-plan. Aucun message n'est perdu.
  • Inbox et idempotence côté consommateur, car un message peut arriver deux fois (livraison at-least-once).
  • Retries avec backoff exponentiel et dead-letter queue.

Transverse

  • Options pattern avec ValidateOnStart(). Les secrets passent par dotnet user-secrets en local, jamais dans Git.
  • Résilience : Microsoft.Extensions.Http.Resilience (Polly v8), déjà inclus dans ServiceDefaults.
  • Health checks /health et /alive, et traces distribuées OpenTelemetry.
  • Sécurité : JWT Bearer émis par Keycloak, policies et IAuthorizationHandler pour les autorisations par ressource (« est-ce que tu es membre de ce workspace ? »).
  • SignalR : un groupe par projet, et les notifications sont poussées depuis les handlers d'événements.

6. Angular 21 : les notions à retenir

  • Standalone partout (plus de NgModules), zoneless (par défaut depuis la v21) et ChangeDetectionStrategy.OnPush.
  • Signals : signal, computed, effect (avec parcimonie), linkedSignal, input(), output(), model().
  • Chargement de données : httpResource() ou resource() pour des requêtes réactives. RxJS reste utile pour les flux complexes (debounce, WebSocket), avec toSignal et toObservable comme ponts.
  • Control flow : @if, @for (track …), @switch, et @defer pour charger des morceaux de page à la demande.
  • inject() plutôt que l'injection par constructeur. Interceptors et guards sous forme de fonctions.
  • État global : NgRx SignalStore (withState, withComputed, withMethods).
  • Formulaires : Reactive Forms typés, ou Signal Forms (encore expérimentaux, à tester).
  • Organisation par feature (features/board, features/projects), avec core/ pour les singletons et shared/ pour l'UI réutilisable. Routes chargées à la demande (loadComponent, loadChildren).
  • Client HTTP généré depuis l'OpenAPI du backend (orval ou openapi-generator) : des types partagés et zéro désynchronisation.
  • Authentification OIDC avec angular-auth-oidc-client (flux Authorization Code + PKCE).
  • UI avec Angular Material et CDK Drag&Drop pour le Kanban, ou Tailwind.

8. CI/CD avec GitHub Actions

PR ouverte ─► ci.yml
  ├─ backend : restore (cache NuGet) → build → tests unitaires et d'architecture
  │            → tests d'intégration (Testcontainers) → couverture → SonarCloud
  ├─ frontend : npm ci (cache) → lint → Vitest → build de production
  ├─ security : CodeQL + scan des dépendances
  └─ e2e : Playwright contre l'application lancée en conteneurs

merge sur main ─► cd.yml
  ├─ numéro de version calculé (semantic-release / Conventional Commits)
  ├─ docker build multi-stage → push GHCR (tags : sha + version)
  ├─ migrations EF (bundle) → Neon
  ├─ déploiement API → Render (deploy hook)   | environnement "production"
  ├─ déploiement front → Cloudflare Pages     | avec approbation manuelle
  └─ smoke test sur /health + GitHub Release
  • Branch protection : pas de merge sans CI verte ni revue.
  • Conventional Commits (feat:, fix:) : le changelog et la version sont générés automatiquement.
  • Environnements GitHub avec secrets séparés et approbation manuelle pour la production.
  • Dependabot ou Renovate pour mettre à jour NuGet, npm et les actions.
  • Dockerfile multi-stage : image finale aspnet chiseled (sans shell, utilisateur non-root). On peut aussi utiliser dotnet publish /t:PublishContainer sans Dockerfile.
  • Workflows réutilisables (workflow_call) et cache des dépendances pour accélérer les builds.

10. Pièges classiques (et questions d'entretien)

  • Sur-architecturer : n'ajoute pas un repository générique au-dessus d'EF Core, le DbContext est déjà un Unit of Work.
  • Domaine anémique : si toutes tes règles métier sont dans les handlers, ton DDD n'en est pas un.
  • Exposer des entités EF directement dans l'API : utilise toujours des DTO.
  • Publier un événement après le commit sans outbox : un crash entre les deux fait perdre le message.
  • Oublier CancellationToken dans la chaîne async, ou appeler .Result / .Wait() sur une tâche.
  • Utiliser effect() pour dériver un état : il faut computed ou linkedSignal.
  • Oublier track dans @for, ou le faire porter sur l'index au lieu de l'identifiant.
  • Mettre des secrets dans appsettings.json ou dans les logs de la CI.
  • Écrire des tests d'intégration sur SQLite ou InMemory alors que la production tourne sur Postgres : utilise Testcontainers.
